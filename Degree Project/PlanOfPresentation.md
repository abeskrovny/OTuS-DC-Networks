## Слайд 2. Проблема и актуальность — 1:00

**Визуал:**
- Слева — график роста параметров LLM (лог-шкала) рядом с ростом требований к bandwidth.
- Справа — схема «бутылочное горлышко»: GPU ждет данных по сети.
- Внизу — плашка: «до 30–50% простоя GPU из-за сетевых задержек».
- **Из диплома:** график из раздела «Актуальность». Если нет — сделать новый минималистичный.

**Что сказать:**
- «Современные LLM обучаются распределенно: тысячи GPU синхронизируют градиенты. Если сеть не успевает — GPU простаивают».
- «Ключевая проблема — не пропускная способность сама по себе, а **хвостовые задержки** (tail latency): синхронный обмен идет со скоростью самого медленного звена».
- «Трафик All-Reduce и All-to-All создает микро-всплески (Incast) — традиционная трехуровневая архитектура с переподпиской здесь не работает».
- «Вторая проблема: ручная настройка сотен коммутаторов — ошибки, дрейф конфигураций, долгий ввод в строй».

**Не забыть:** четко разделить **две проблемы** — сетевая (архитектура) и эксплуатационная (автоматизация). Это задает структуру всей презентации.

## Слайд 3. Архитектура AI-фабрики: обзор — 1:00

**Визуал:**
- **Главный рисунок диплома** — общая схема Fat-Tree (Clos) с тремя контурами. Самый крупный слайд.
- Три цветных контура:
  - 🟦 Compute/Backend — 8×400G RoCEv2
  - 🟩 Frontend — 2×25G TCP/IP
  - 🟨 Management/OoB — 1G IPMI
- Подпись: «переподписка 1:1».
- **Из диплома:** главная схема раздела «Архитектура».

**Что сказать:**
- «Выбрана неблокируемая топология Клоза с переподпиской 1:1 — обязательное условие, чтобы синхронный обмен градиентами не упирался в oversubscription».
- «Сеть разделена на три изолированных контура: Backend для GPU-трафика, Frontend для управления и стореджа, OoB для IPMI — чтобы аварийный доступ не зависел от рабочей сети».
- «Для Backend выбран **RoCEv2**, а не InfiniBand: открытый стандарт, нет vendor lock-in, нативная L3-маршрутизация, работает поверх обычного Ethernet».
- «RoCEv2 требует **lossless-настройки** (PFC, ECN) — это часть проекта, а не «просто включить»».

**Не забыть:** подчеркнуть, почему **не InfiniBand** — частый вопрос комиссии. Служит «зонтиком» для слайдов 4–6.

## Слайд 4. Backend / Compute Network (8×400G RoCEv2) — 1:45

**Визуал:**
- **Из диплома:** схема Backend-контура (GPU-сервер → Leaf → Spine) с подписанными 8×400G. Если в дипломе только общая схема — вырезать Backend-часть и увеличить.
- **Таблица расчетов** (фрагмент из диплома или собрать на слайде):
  - Кол-во GPU-серверов: N
  - Аплинков на сервер: 8×400G
  - Портов на leaf: 32×400G
  - Кол-во leaf: `ceil(N × 8 / 32)`
  - Кол-во spine: `ceil(leaf × аплинки / порты spine)`
  - Переподписка: **1:1** (non-blocking)
- **Плашка параметров:** MTU 9216, PFC, ECN, DSCP-очереди.
- Bisection bandwidth = X Tbps (из диплома).

**Что сказать:**
- «Backend — самый критичный контур: по нему идет синхронизация градиентов. Расчет начинается с числа GPU-серверов и требуемой переподписки».
- «Для неблокирующей топологии 1:1 число портов spine ≥ числа аплинков leaf — отсюда формула: `leaf = N_servers × uplinks / ports_per_leaf`».
- «На каждый сервер — **8×400G**, потому что GPU-трафик All-Reduce идет одновременно со всех 8 GPU; агрегация на 400G дает нужную пропускную способность на узел».
- «Ключевые настройки: **MTU 9216** (jumbo frames), **PFC** для lossless, **ECN** для управления перегрузками, **DSCP** для приоритизации RDMA».
- «Виртуальное окружение: контур смоделирован на **vEOS** — spine/leaf-пары с BGP Unnumbered, проверена сходимость и передача трафика».

**Не забыть:** 8×400G на сервер — **расчетная величина** под 8 GPU (8 × 400G = 3.2 Tbps), а не «на всякий случай».

## Слайд 5. Frontend Network (2×25G TCP/IP) — 1:30

**Визуал:**
- **Из диплома:** схема Frontend-контура с VLAN и LACP. Если в дипломе только общая — вырезать фрагмент.
- **Таблица расчетов:**
  - Аплинков на сервер: 2×25G (LACP)
  - Переподписка: **4:1** (обосновать)
  - Uplink в WAN: N×100G
  - VLAN-сегментация: management / storage / services
- Иконки: файрвол, балансировщик, storage-кластер.
- Плашка: «TCP/IP стек, стандартные VLAN, без RDMA».

**Что сказать:**
- «Frontend — контур общего назначения: доступ к стореджу, обновления ПО, телеметрия, внешние сервисы. Здесь **не нужен lossless** — обычный TCP/IP».
- «Расчет: **2×25G на сервер** с LACP — достаточно для служебного трафика, не конкурирует с Backend за дорогие 400G-порты».
- «Переподписка **4:1** — потому что трафик не синхронный и не критичен к хвостовым задержкам, как All-Reduce».
- «VLAN-сегментация: отдельные VLAN под management, storage и внешние сервисы — базовое требование безопасности и изоляции».
- «Виртуальное окружение: frontend-leaf с VLAN-транками и LACP-агрегацией; проверена изоляция сегментов».

**Не забыть:** подчеркнуть **контраст с Backend** — здесь другие требования (не latency, а функциональность и стоимость).

## Слайд 6. Management / Out-of-Band Network (1G IPMI/OoB) — 1:30

**Визуал:**
- **Из диплома:** схема OoB-контура с jump-host и BMC/IPMI. Если только общая — вырезать фрагмент и увеличить, добавить подпись «физически изолирован».
- **Таблица расчетов:**
  - 1×1G на каждый BMC сервера
  - 1×1G на management-порт каждого коммутатора
  - Кол-во OoB-коммутаторов: `ceil(всего устройств / 24 или 48)`
  - Изоляция: отдельный VRF / физически отдельная сеть
- Плашка: «Доступен, даже если Backend и Frontend лежат».
- Иконка: замок / «emergency access».

**Что сказать:**
- «OoB — **аварийный контур**. Задача — обеспечить доступ к устройству, даже если основная сеть полностью недоступна».
- «Расчет: **1×1G на каждый BMC/IPMI** сервера и management-порт каждого коммутатора. Коммутаторы OoB подбираются по числу портов 24/48».
- «Ключевое решение — **физическая изоляция**: OoB не пересекается с Backend и Frontend ни на L2, ни на L3. Отдельные коммутаторы, отдельная адресация, отдельный путь доступа».
- «Доступ — только через **jump-host** с аудитом; прямой доступ к BMC из рабочей сети закрыт».
- «Виртуальное окружение: OoB смоделирован как отдельный сегмент в vEOS; проверено, что при «падении» Backend доступ к management сохраняется».

**Не забыть:** это слайд про **эксплуатационную зрелость**, а не про скорость. Сказать явно.

## Слайд 7. Underlay-маршрутизация: BGP Unnumbered — 1:15

**Визуал:**
- **Из диплома:** сравнительная таблица протоколов Underlay (в README — «Таблица 2» со сбитой нумерацией). На слайде оставить **3–4 строки**: BGP Unnumbered / OSPF / IS-IS по критериям: масштабируемость, память, сходимость, зрелость. Полную таблицу — в раздатку.
- Справа — мини-схема: два коммутатора, IPv6 Link-Local, подпись «RFC 5549/8950».
- Логотипы-отсылки: Meta, Microsoft.

**Что сказать:**
- «В Underlay выбран **BGP Unnumbered** — де-факто стандарт для AI-фабрик, используют Meta, Microsoft, Google».
- «Почему не OSPF/IS-IS: link-state протоколы при масштабировании дают LSA-флуд и нагрузку на CPU; BGP масштабируется лучше и дает больше контроля через policy».
- «Плюсы BGP Unnumbered: **Zero-Touch** — сессия поднимается через IPv6 Link-Local без назначения IP; минимальный memory footprint; быстрая сходимость с BFD».
- «Связано с автоматизацией: не нужно вручную прописывать IP на каждом линке — меньше конфигурации, меньше ошибок».

**Не забыть:** связать выбор протокола с темой автоматизации — «меньше ручной конфигурации = меньше дрейфа».

## Слайд 9. GitOps: зачем это нужно поверх Ansible — 1:15

**Визуал (создать):**
- **Слева** — «Ansible-only»: стрелка от инженера к устройству, подпись «кто-то запустил — и все».
- **Справа** — «GitOps»: цепочка `Git (review) → CI (validate) → CD (deploy) → reconciliation`, иконка Git-ветки.
- Внизу — 4 иконки-принципа: 📜 Декларативность, 🔀 Версионирование, 🤖 Автоматизация, 🔁 Непрерывная сверка.
- Стиль — в единой визуальной семье с рисунками диплома (оранжевый/фиолетовый акцент для Git).

**Что сказать:**
- «GitOps — не инструмент, а **операционная модель**. Git становится единственным источником истины: в репозитории лежит желаемое состояние инфраструктуры».
- «Четыре принципа: **декларативность**, **версионирование**, **автоматическая доставка** через CI/CD, **непрерывная сверка** желаемого и фактического состояния».
- «Что дает поверх Ansible: **аудируемость** (кто, что, когда), **ревью через Merge Request**, **предсказуемый откат** — откатить коммит».
- «И главное — **drift detection**: если кто-то вручную поправил коммутатор, система это увидит и откатит/предупредит».

**Не забыть:** это «новый» блок — говорить уверенно, не спеша.

## Слайд 10. NetBox как Source of Truth — 1:15

**Визуал (создать):**
- **Скриншот интерфейса NetBox** (устройства / интерфейсы / IP) — лучше реальный из стенда.
- Рядом схема: `NetBox` в центре, стрелки к «IPAM», «DCIM», «REST API», «Ansible».
- Подпись: «Single Source of Truth — единый источник истины».

**Что сказать:**
- «В качестве источника истины выбран **NetBox** — объединяет IPAM (управление IP) и DCIM (управление инфраструктурой): устройства, интерфейсы, VLAN, площадки в одном месте».
- «NetBox отдает данные через **REST API** — из него Ansible и шаблоны берут информацию для генерации конфигураций».
- «Инженер вносит изменение один раз — в NetBox, — и оно автоматически распространяется в конфигурацию».
- «⚠️ Ограничение: **NetBox сам по себе не GitOps**. Нет ветвления и версионирования в Git-смысле. NetBox — источник данных, Git — источник *состояния*».

**Не забыть:** честно проговорить ограничение NetBox — показывает глубину и снимает вопрос «почему не Nautobot?».

## 💡 Раздатка (не на слайды)

2. **Формулы расчетов** одной страницей:
    Backend: leaf = ceil(N_srv × uplinks_per_srv / ports_per_leaf)
    spine = ceil(leaf × uplinks_per_leaf / ports_per_spine)

    OoB: switches = ceil((N_srv + N_switches) / ports_per_oob_switch)

## 🎯 Вероятные вопросы комиссии — подготовленные ответы

| Вопрос | Ответ |
|--------|-------|
| Чем GitOps отличается от обычного CI/CD для сети? | Непрерывная сверка (reconciliation) + Git как единственный источник истины |
| Почему NetBox, а не Nautobot? | Зрелость, IPAM+DCIM, REST API; Nautobot — направление развития |
| Как обеспечивается lossless для RoCEv2? | PFC + ECN, выделенные QoS-очереди, MTU 9216 |
| Что если кто-то руками поправит коммутатор? | Drift detection поймает и откатит/алертит |
| Почему не InfiniBand? | Открытый стандарт, нет vendor lock-in, нативная L3, работает поверх Ethernet |
| Почему 8×400G на сервер? | 8 GPU × 400G = 3.2 Tbps — расчетная величина под All-Reduce |
| Что проверено на стенде? | vEOS: генерация конфигов, ZTP-сценарий, валидация транспорта, изоляция контуров |
